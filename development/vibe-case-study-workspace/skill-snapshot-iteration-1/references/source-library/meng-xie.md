# Meng Xie Case-Study Source Library

Source: [Meng Xie AI-Native Design Portfolio](https://mengxie.me/)  
Research snapshot: 2026-08-24  
Detailed corpus and source boundaries: [validated Pattern Matrix](../../../meng-case-study-pattern-matrix-validated.md)

Use these cards to generate better questions and project-specific candidate statements. Do not copy wording, headings, visual styling, metrics, or outcomes from the source cases.

## MX-01 — Personal constraint sharpens scope

- **Source cases:** Little Color World; Passport Photo Generator; Parental Leave Calculator.
- **Original signal:** A specific personal situation constrained the minimum useful product.
- **Transferable interpretation:** A narrow trigger can explain scope more credibly than a broad market claim.
- **Applicable archetypes:** Product Utility.
- **Required project evidence:** Concrete situation, working task, and real-use receipt.
- **Candidate question:** What happened that made you build the first version, and what did that situation force you to omit or simplify?
- **Adapted-statement formula:** Because [specific situation], I limited the first version to [essential capability], rather than [plausible but unnecessary scope].
- **Factual risks:** Inflating a personal frustration into a validated market need.
- **Proof treatment:** Trigger visual, minimum-flow demo, or author-reported use receipt.

## MX-02 — Feedback visibly changes the next version

- **Source cases:** Parental Leave Calculator; Bloom.
- **Original signal:** A real request caused an inspectable product change.
- **Transferable interpretation:** Feedback matters when the reader can see what changed because of it.
- **Applicable archetypes:** Product Utility; Product Experiment; Workflow / System.
- **Required project evidence:** Feedback receipt and a version, workflow, or interface difference.
- **Candidate question:** Which request changed what you built next, and where is that change visible?
- **Adapted-statement formula:** After [user/group] asked for [need], I changed [specific part], which shifted the product from [old understanding] toward [new understanding].
- **Factual risks:** Calling an unsourced change feedback-led.
- **Proof treatment:** Feedback excerpt beside a before/after or v1/v2 comparison.

## MX-03 — Production context reveals design constraints

- **Source cases:** Production Codebase Prototyping; Status Scheduling Subscriber UX.
- **Original signal:** A working environment exposed states and constraints that static mockups did not.
- **Transferable interpretation:** Code is valuable when it changes the design decision, not when it merely increases fidelity.
- **Applicable archetypes:** Product Experiment.
- **Required project evidence:** Real build or state, discovered constraint, and resulting decision.
- **Candidate question:** What became visible only after the idea ran in the real environment?
- **Adapted-statement formula:** Building [experience] in [real environment] exposed [constraint], so I changed [decision].
- **Factual risks:** Treating code volume or technical difficulty as product impact.
- **Proof treatment:** Physical-device demo, edge state, or alternative comparison.

## MX-04 — Repeated friction becomes a workflow

- **Source cases:** WhatsApp Production Audit Platform; Subs Dogfooding; AI-Native Figma SoTs.
- **Original signal:** Several people repeated a fragmented process that could be reorganized into one workflow.
- **Transferable interpretation:** Describe the before sequence, then show the new input, decision, and output model.
- **Applicable archetypes:** Workflow / System.
- **Required project evidence:** Repeated actors or occurrences, concrete before flow, working system, and real output.
- **Candidate question:** Which steps and tools repeated, and what now connects them?
- **Adapted-statement formula:** [Number or list of disconnected steps] became [one coherent workflow] organized around [user task].
- **Factual risks:** Presenting a collection of utilities as a system without a shared task model.
- **Proof treatment:** Before/after workflow diagram or input-to-output demo.

## MX-05 — Packaging separates reuse from the creator

- **Source cases:** AI-Native Figma SoTs; Vibe Designing; AI-Native Prototyping Playbook.
- **Original signal:** Judgment became installable, repeatable, or teachable.
- **Transferable interpretation:** A workflow travels only when people can access its logic without relying on its creator.
- **Applicable archetypes:** Workflow / System.
- **Required project evidence:** Packaged artifact and external use.
- **Candidate question:** What did you encode, and how could someone else run or learn it without you?
- **Adapted-statement formula:** I encoded [judgment] into [artifact], allowing [others] to [outcome] without [old creator dependency].
- **Factual risks:** Claiming adoption because an artifact was merely available.
- **Proof treatment:** Installable artifact, documented workflow, and external-use receipt.

## MX-06 — Human-AI handoff beats full automation

- **Source case:** Human-AI Collaborative Design.
- **Original signal:** A hard quality boundary forced precision work back to human judgment.
- **Transferable interpretation:** The useful lesson is the changed division of labor, not generic human-in-the-loop language.
- **Applicable archetypes:** Product Experiment; Workflow / System; Practice Note.
- **Required project evidence:** Failed output, human intervention, and verified improvement.
- **Candidate question:** Where did automation fail, and what did you deliberately take back?
- **Adapted-statement formula:** When the agent failed at [constraint], I delegated [repeatable work] but retained [judgment], producing [verified result].
- **Factual risks:** Inventing an AI-craft lesson without a concrete failure.
- **Proof treatment:** Failed/result comparison or annotated handoff sequence.

## MX-07 — Choose tools by task fit

- **Source cases:** Pencil.dev Evaluation; AI-Native Deck Creation.
- **Original signal:** Tools were compared against a real decision context, including unsuitable uses.
- **Transferable interpretation:** Tool judgment is stronger than naming a preferred tool.
- **Applicable archetypes:** Product Experiment; Practice Note.
- **Required project evidence:** Comparative trial and explicit selection criteria.
- **Candidate question:** Which task did each tool handle well, and where did it fail your quality bar?
- **Adapted-statement formula:** I used [tool] for [task] because [capability], but kept [other tool/manual method] for [precision or judgment].
- **Factual risks:** Declaring a universal winner from one project.
- **Proof treatment:** Decision matrix or same-task output comparison.

## MX-08 — Information architecture is the product

- **Source cases:** AI Design Learning Hub; AI-Native Prototyping Playbook.
- **Original signal:** Organizing information reduced the cost of finding and acting on it.
- **Transferable interpretation:** Explain the behavior enabled by the structure, not only the categories.
- **Applicable archetypes:** Workflow / System.
- **Required project evidence:** Before-state discovery friction and inspectable architecture.
- **Candidate question:** What could people find or do after the information was reorganized?
- **Adapted-statement formula:** Reorganizing [fragmented material] around [user task] made [specific action] coherent.
- **Factual risks:** Treating a taxonomy alone as user impact.
- **Proof treatment:** Before-state map beside the new navigation or learning path.

## MX-09 — Contribution expands product scope

- **Source cases:** Bloom; AI-Powered Group Order.
- **Original signal:** Participation changed ownership, content, or product capability.
- **Transferable interpretation:** Contribution is stronger than reaction because it alters what the product contains or becomes.
- **Applicable archetypes:** Product Utility; Workflow / System.
- **Required project evidence:** Contribution behavior and resulting product change.
- **Candidate question:** What did another person add or request that materially changed the product?
- **Adapted-statement formula:** When [participants] contributed [request/content/capability], the product expanded from [old scope] to [new scope].
- **Factual risks:** Equating comments or reactions with contribution.
- **Proof treatment:** Contributor-to-change map or request beside implemented result.

## MX-10 — Distribution creates product trade-offs

- **Source cases:** Subs Dogfooding; AI-Native Figma SoTs.
- **Original signal:** Installation, access, security, and maintenance shaped whether the workflow could travel.
- **Transferable interpretation:** Distribution is part of the experience for internal tools and reusable systems.
- **Applicable archetypes:** Workflow / System; Product Experiment.
- **Required project evidence:** Channel comparison, setup constraint, and real distribution behavior.
- **Candidate question:** What prevented someone from using the workflow without your help?
- **Adapted-statement formula:** [Distribution constraint] made [channel] unsuitable, so I chose [approach] to preserve [access or control].
- **Factual risks:** Hiding setup friction or calling facilitated access self-serve adoption.
- **Proof treatment:** Distribution decision matrix or setup-to-use walkthrough.

## MX-11 — Second-order use is stronger than raw reach

- **Source cases:** AI-Native Deck Creation; AI-Native Prototyping Playbook.
- **Original signal:** People later taught, reused, or redistributed the method to others.
- **Transferable interpretation:** A workflow begins to belong to a team when use no longer depends on its creator.
- **Applicable archetypes:** Workflow / System.
- **Required project evidence:** Teaching, invitation, reuse, contribution, or redistribution that happened without creator facilitation.
- **Candidate question:** Did returning users introduce, invite, teach, or redistribute the workflow to anyone else without you?
- **Adapted-statement formula:** [Returning users] began [bringing/teaching/distributing] the workflow to [new participants] without [creator dependency].
- **Factual risks:** Converting facilitated trials, repeat use, views, or reactions into second-order adoption.
- **Proof treatment:** Anonymized invitation, teaching artifact, reuse trail, or Adoption block. If unconfirmed, use a **Next signal** block only.

## MX-12 — One artifact earns a broader belief

- **Source cases:** Recurs across the portfolio.
- **Original signal:** A concrete project progression ends in one bounded, transferable conclusion.
- **Transferable interpretation:** State the belief only after the events establish it.
- **Applicable archetypes:** All.
- **Required project evidence:** Causal chain from trigger through decision to result.
- **Candidate question:** What would you now do differently on a similar project, and which event taught you that?
- **Adapted-statement formula:** This project showed me that [bounded belief] when [conditions].
- **Factual risks:** Generating a symmetrical slogan or generic principle by default.
- **Proof treatment:** Insight block near the conclusion, only when the body already earns it.

## Presentation patterns

- **Hero claim:** State artifact, difference, and significance without leading with the AI tool.
- **Proof strip:** Surface only high-value states with a known basis.
- **Variable middle:** Name sections after actual decisions, tasks, or project stages.
- **Claim-to-visual pairing:** Place demos, comparisons, and receipts beside the claim they support.
- **Proof block:** Emphasize a verified impact, attributed behavior, earned insight, or explicitly hypothetical next signal.

Keep source facts and current-project facts separate. A source pattern can generate a candidate statement; only current-project evidence determines its status and public wording.
